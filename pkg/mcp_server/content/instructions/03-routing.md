# Routing and fan-out semantics

- Some required input params are routing parameters: they select which endpoint the request is sent to, they do not filter the data returned. In some cases they are server variables substituted into the endpoint URL itself, eg `region` (`aws`) or `deployment_name` (`databricks_workspace`); in others they are path parameters, eg `project` / `zone` (`google`), `subscriptionId` / `resourceGroupName` (`azure`). Account-global list operations return the same result set regardless of which endpoint is routed to.
- To answer "how many X per region/project/subscription", use an output field that carries the per-item scope (eg `bucket_region`) rather than the routing param, or use a resource whose list operation is scoped at that grain.
- `WHERE <routing_param> IN ('a','b','c')` dispatches one async request per value and unions the results. Use this for multi-region or multi-project inventory instead of running one query per value. The routing param value is materialised as a column, so it can appear in the select list and in `GROUP BY`.
- A hard failure (eg a 400 from an opt-in or disabled region) from any member of an `IN` fan-out fails the whole query: remove opt-in, disabled or inaccessible members from the list and retry, bisecting if the failing member is not obvious. Members that merely return 404 "not found" contribute zero rows without failing the query (see error handling).
